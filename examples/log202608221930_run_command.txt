--- 模式1: Role Prompting（角色设定） ---
我来用一个餐厅的比喻解释CAP定理。

想象你经营着一家连锁餐厅，有三家分店（A、B、C），它们共同维护一份菜单（数据）。

**C（一致性）**：就像所有分店的菜单必须完全一样。如果A店改了菜价，B、C店必须立刻同步，否则顾客在A店看到鱼香
肉丝38元，到B店却要42元，就会混乱。

**A（可用性）**：就像餐厅必须随时能接待顾客。哪怕B店网络断了，顾客敲门时也得能点菜，不能让人吃闭门羹。

**P（分区容错性）**：就像三家分店之间的电话线路偶尔会断。这是现实世界无法避免的——网络总会出问题。

**CAP定理的核心结论是：当电话线路断了（发生分区）时，你必须在“让所有店菜单一致”和“让每家店都能继续营业”之间
二选一。**

- 
**选C放弃A**：B店网络断了，就干脆关门不营业，等线路恢复、菜单同步后再开门。这样保证菜单永远一致，但顾客会吃
闭门羹。
- 
**选A放弃C**：B店网络断了，照样营业，但先用自己的旧菜单（可能价格过时）。顾客能点菜，但可能被多收或少收钱，
等线路恢复后再补同步。

**为什么不能同时选C和A？** 
因为当线路断了，你无法既让B店立刻响应顾客（A），又保证它用的是最新菜单（C）——除非你让B店等线路恢复（牺牲A）
。

**现实中的选择**：
- 银行转账系统：选C，宁可交易失败也不能账目不一致（钱不能凭空多或少）。
- 社交平台点赞数：选A，点赞数稍微延迟显示没关系，但用户必须能随时刷出页面。
- 购物车系统：通常选A，允许短暂不一致（比如库存显示有货但实际没了），但保证用户能下单。

**一句话总结**：CAP定理就是告诉你——网络故障时，你必须在“准确”和“及时”之间做个取舍，没有完美方案。就像餐厅线
路断了，你不可能既让B店正常营业，又保证它菜单和A店完全同步。

**第二步：计算三管同时打开时的净注水速度**  
进水管增加水量，出水管减少水量，所以净注水速度为：  
[
\frac{1}{6} + \frac{1}{8} - \frac{1}{12}
\]  

先通分，6、8、12的最小公倍数是24：  
[
\frac{1}{6} = \frac{4}{24}, \quad \frac{1}{8} = \frac{3}{24}, \quad \frac{1}{12} = \frac{2}{24}
\]  
所以：  
[
\frac{4}{24} + \frac{3}{24} - \frac{2}{24} = \frac{5}{24}
\]

=== 3. 生产环境成本优化手段 ===
  • 模型路由: 简单问题用小模型(deepseek-chat)，复杂问题用强模型(deepseek-reasoner)，可省 50%+ 成本
  • Prompt 缓存: DeepSeek 支持 context caching，重复的 system prompt 命中缓存部分输入价格打 1 折
  • 语义缓存: 对高频重复问题直接返回缓存答案，不调用 LLM（如 GPTCache）
  • 流式输出: 提升用户体验，不省成本但降低超时重试带来的浪费
  • Batch API: OpenAI/DeepSeek 都有 Batch API，非实时任务用批量接口可省 50%
  • 压缩上下文: 用摘要替代长对话历史，减少 prompt tokens
  • 设置 max_tokens: 防止 LLM 无限输出导致成本失控
  • 监控告警: 对 Token 用量设置日预算上限，超阈值告警（本项目的 TokenTracker 就是基础版）
